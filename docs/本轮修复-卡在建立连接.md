# 本轮修复：为什么「第一条命令要等 66 秒，后面全秒失败」

## 一句话

**那 66 秒不是手机慢，是我们自己把自己锁死了。** 根因找到了，也修了。

## 二、坏消息：卡在「拉起手机端」这一步

```
[189.654] 向手机发 shell: pm list packages
[189.656]    失败，返回 -1            ← 2 毫秒就失败
```

而更早的那条：

```
[123.438] ── 手机自报家门 ──
[189.629]    getprop sys.usb.config = [mtp,adb]     ← 中间隔了 66 秒
```

**第一条 shell 命令花了 66 秒，后面全部秒失败。**

---

## 三、根因：我们自己造的一个死锁

这台车机的 ADB 驱动，`ReadFile` 是**阻塞**的 —— 没数据时它会一直等，等到有数据或者它自己超时（几十秒）才返回。

而我们的代码里，转发线程每 10 毫秒就做一次：

```c
ADBP_LOCK();
r = adb_pump(&g_adb, 0);      /* ←「0」是超时 0，注释里写着「非阻塞，收不到就算了」 */
ADBP_UNLOCK();
```

**那句注释是错的假设。** 超时参数根本传不到驱动层：`ReadFile` 照样阻塞几十秒。
于是转发线程**握着 ADB 锁**一握就是几十秒。

而会话线程要发 `getprop`、`pm list packages`，**这些都必须先拿到同一把锁** ——
于是全被挡在门外，干等。这就是那 66 秒：

```
转发线程：拿到锁 → ReadFile 阻塞（没数据，等 60 秒）→ 松锁
会话线程：……一直在门口等…… → 终于拿到锁 → 发出命令（几毫秒就完成）
```

**而且是死锁结构**：手机要有数据可发，得先收到我们的命令；而我们的命令发不出去，因为锁在转发线程手里。它每次都是靠驱动自己「读超时放弃」才勉强解开。

### 解开之后还留下一个烂摊子

那次阻塞读把 USB 管道拖进了错误状态。之后就出现这个现象：

```
[189.656]    失败，返回 -1         ← 2 毫秒
```

秒失败，但统计里却是 **「写失败 0 次」** —— 因为 `WriteFile` **没报错，只是写了 0 个字节**
（驱动内部发送缓冲满了，它不报错，只是不接收）。我们原来把「写了 0 字节」直接当失败返回，
于是后面每一条命令都是秒退。最后整条流对不齐：

```
[195.097] 转发器 | ADB 通道断了（错误 -2）
```

## 四、怎么修的

### 主修：给设备配一个**专用读线程**

```
        ┌──────────────┐  阻塞读    ┌──────────────┐
设备 ──→│ 读线程(专用)  │──────────→│  512KB 环形缓冲 │──→ 应用层 ce_read（永远有界）
        └──────────────┘            └──────────────┘
```

- **读线程**：独占设备做阻塞读，读到就往环形缓冲里放。它**不碰 ADB 锁**。
- **`ce_read`（应用层）**：只从环形缓冲取，一秒都不会被设备卡住 —— 不管驱动是不是阻塞的。
- 于是那把 ADB 锁的持有时间**再也不可能被设备拖长**。

读线程还带了健康检查：日志里现在会打印
`读线程 活着/已退出，环形缓冲还剩 N 字节（容量 524288），缓冲满丢过 N 次`
—— 一眼就能分清「设备不行了」和「我们自己的读线程没了」。

### 附带修掉的三处

| # | 修了什么 | 为什么 |
|---|---|---|
| 1 | `WriteFile` 写了 0 字节时**重试最多 20 次**（≈100ms），并单独计数 | 不再把「驱动暂时满」当成「设备坏了」秒退 |
| 2 | `adb_open` 失败时**把通道槽位还回去** | 通道表只有 8 个槽位；原来失败不释放，失败 8 次之后**再也发不出任何命令**。这正好对应日志里「第一条成功、后面全失败」的形态 |
| 3 | 错误码**紧跟 `CreateFileW` 取** | 原来在 `cl_log()` 之后才取，而 `cl_log` 自己会刷盘，把错误码冲成了 258。所以日志里那行「试过：ADB1:(错误258) ADB0:(错误258)…」六个全一样 —— 258 是刷盘的错，不是打开设备的错 |

## 五、下一趟应该看到什么

改完之后，`getprop` / `pm list packages` 这类命令应该**几毫秒就回来**，
日志里会很快走到：

```
【阶段 2/8】拉起手机端智能车载（ADB shell）
   手机里的包名清单（原样记录，供离线核对）：
   package:com.vivo.xxx / package:com.baidu.carlife / …
   拉起手机端智能车载   OK   （或明确写出为什么没起来）
【阶段 3/8】连接控制通道（经 ADB 转发到手机的 7240）
【阶段 4/8】CarLife 协议握手
```

**手机上如果弹权限框，请点「允许」。**

万一还是失败，日志现在能直接指出是哪一环：
- 「读线程 已退出」→ 设备/驱动层的问题；
- 「环形缓冲还剩 … 缓冲满丢过 N 次」→ 我们的读线程跟不上，要调大；
- 「失败，返回 -1/-2/-3」且命令名清楚 → 是 adb 通道层；
- 「手机没回应协议版本」→ 已经到 CarLife 协议层了，那是另一个话题。
