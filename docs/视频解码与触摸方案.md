# 视频解码、画面渲染、触摸回传 —— 方案与实测依据

> 本文件记录「收到视频帧之后」这一段的设计。所有协议事实来自
> `Doris-duo/CarLife-MD-Lib`（Apache-2.0，源自百度 CarLife-Vehicle-Lib）。
> 标注：**【实证】**= 已在真机验证 ·【代码原文】= 参考实现里写的 ·【推断】= 尚待验证

## 一、先解决"到底是什么编码"——别猜

### 【最便宜的诊断】打印首帧头部

`src/huclient.c` 已经做了这件事：收到第一帧时把前 12 字节按十六进制打进窗口，
并用 `cl_guess_codec()` 给出判断：

| 首字节 | 判断 |
|---|---|
| `FF D8` | **JPEG**（MJPEG） |
| `00 00 00 01` | **H.264**（4 字节起始码） |
| `00 00 01` | **H.264**（3 字节起始码） |
| 全零 | 没有真实数据 |

**这一步决定了后面所有工作量，所以放在最前面。**
- 若为 **JPEG** → 解码约 1000 行代码，难度低
- 若为 **H.264** → 需要完整解码器，难度高一个量级

### 【代码原文】存在 JPEG 路径

`CTranRecvPackageProcess.h` 里有：

```c
MSG_CMD_VIDEO_ENCODER_JPEG     = 0x00018056,   // 车机→手机：请求改用 JPEG
MSG_CMD_VIDEO_ENCODER_JPEG_ACK = 0x00010057,   // 手机→车机：同意
```

→ 如果手机支持，**可以主动要求它推 JPEG 而不是 H.264**，
这就把解码难度从"月"降到"周"。`cl_send_video_encoder_jpeg()` 已实现。

## 二、⭐ 关键杠杆：分辨率和帧率是我们定的

【代码原文】`S_VIDEO_ENCODER_INIT { width, height, frameRate }` 由**车机**发给手机，
手机回 `VIDEO_ENCODER_INIT_DONE` 告知**实际采用值**（`huclient.c` 已解析并显示）。

还有动态调整通道：
```c
MSG_CMD_VIDEO_ENCODER_FRAME_RATE_CHANGE      = 0x0001800C,
MSG_CMD_VIDEO_ENCODER_FRAME_RATE_CHANGE_DONE = 0x0001000D,
```

### 性能预算【推断】

老 ARM 车机上软解 H.264 的能力大致按"每秒处理像素数"衡量：

| 分辨率 @ 帧率 | 每秒像素 | 老 ARM 软解可行性 |
|---|---|---|
| 768×480 @ 30 | 11.0 M | ✗ 基本不可能 |
| 768×480 @ 15 | 5.5 M | ✗ 悬 |
| **480×272 @ 15** | **2.0 M** | ✅ 大概率可以 |
| **480×272 @ 10** | **1.3 M** | ✅ 稳 |

→ **第一版就请求小分辨率低帧率**，先"能看"，再谈流畅。
导航类用途 10–15 帧完全够用。

## 三、解码器候选（都是纯 C，可移植到 CeGCC）

| 方案 | 项目 | 许可证 | 状态 |
|---|---|---|---|
| H.264 基线 | `oneam/h264bsd` ★211 | 需核对 | 待定（要看实测编码） |
| **JPEG** | **nanojpeg 1.3.5（Martin J. Fiedler）** | **MIT** | ✅ **已集成且已验证可用** |
| ❌ 不适用 | `lieff/minih264` | CC0 | **是编码器不是解码器，方向反了** |

### JPEG 解码器：已集成并验证 ✅

源码在 `src/third_party/nanojpeg.c`（919 行，MIT，保留原始版权声明）。

**为什么选它**：单文件、纯 C、917 行、专为嵌入式设计；而且**自带 WinCE 分支**。
⚠ 但它的 `NJ_USE_WIN32` 那条路用的是 **x86 内联汇编**（`rep stosb`），
**在 ARM 上根本编不过** —— 必须走默认的 `NJ_USE_LIBC=1`（用 coredll 提供的
malloc/free/memset/memcpy）。这个坑已经踩过并确认。

**验证方式**（CI 每次自动跑）：

1. `scripts/make_test_jpeg.py` 生成一个**结果完全可预测**的最小 JPEG ——
   所有 DCT 系数为 0，反量化后全 0，加 128 电平偏移 → **整幅图必然恒为 128 灰**。
   Huffman 表自定义（JPEG 允许），所以文件只有 141 字节。
2. 在 CI **主机**上用 gcc 编译运行 `src/third_party/test_nanojpeg.c`，
   断言**每一个像素都等于 128**。
   主机的理由：我们的产物是 ARM WinCE PE，跑不进 CI 的 x86 机器；
   但算法是同一份源码，主机跑通即证明算法正确。
3. 另用 CeGCC 单独编译一次，证明**能为 ARM 编译**。

实测输出：

```
解码结果: 8x8  灰度
✅ 全部 64 个像素都是 128 —— JPEG 解码器工作正常
✅ nanojpeg 能为 ARM/WinCE 编译
```

> 这样就不用「等车机回来才发现解码器写错了」。

## 四、画面渲染

【实证】车机上 `DDRAW.dll` 存在（早期探针已确认）。

| 方式 | 优点 | 缺点 |
|---|---|---|
| **GDI**（`StretchDIBits`） | 简单、一定能用 | 慢，小分辨率下可能勉强够 |
| **DirectDraw**（直接写后备表面） | 快得多 | 需要正确初始化，老驱动有坑 |

→ 先用 GDI 打通，再视帧率决定是否换 DirectDraw。

## 五、触摸回传【代码原文】

**注意消息 ID 是 `0x0006` 前缀 —— 触摸是独立通道**（对应 9300/9340）。

```c
MSG_TOUCH_ACTION           = 0x00068001,
MSG_TOUCH_ACTION_DOWN      = 0x00068002,
MSG_TOUCH_ACTION_UP        = 0x00068003,
MSG_TOUCH_ACTION_MOVE      = 0x00068004,
MSG_TOUCH_SINGLE_CLICK     = 0x00068005,
MSG_TOUCH_DOUBLE_CLICK     = 0x00068006,
MSG_TOUCH_LONG_PRESS       = 0x00068007,
MSG_TOUCH_CAR_HARD_KEY_CODE= 0x00068008,
```

报文（protobuf，全是 int32）：
```protobuf
message CarlifeTouchAction { required int32 action=1; required int32 x=2; required int32 y=3; }
message CarlifeTouchSinglePoint { required int32 x=1; required int32 y=2; }
```

**坐标换算**：车机屏幕坐标 → 手机画面坐标，需要按分辨率比例缩放
（手机画面分辨率由 `VIDEO_ENCODER_INIT_DONE` 告知）。

硬件按键（`KEYCODE_*`）也在这条通道上：`HOME`/`PHONE_CALL`/`NAVI`/`MEDIA` 等，
可以直接映射到车机面板按键。

## 六、包头长度的一个待确认点

【代码原文】包头长度分两类：
- **CMD / CTRL 通道 = 8 字节**
- 其余（VIDEO/MEDIA/TTS/VR）= 12 字节

触摸通道（9300）按端口命名习惯对应代码里的 `CTRL_CHANNEL`，
**推断应使用 8 字节包头**，但**尚未实证**。第一版实现时两条都试，以能收到
手机响应的那条为准。
