# 路线验证：我们走的路，和百度官方走的是不是同一条？

> 问题：「安卓智能车载是怎么走 CarLife / 亿连通道投屏到车机的？
> 你走的路和它有没有不同？这条路到底通不通、最后能不能在我这台 WinCE 车机上跑起 Jovi InCar？」

**结论先说：同一条路，而且是百度官方自己写下来的那条。**
下面每一条都有出处，不是推测。

---

## 证据 ①：百度官方的车机端（HU）协议库，就是用 `adb forward`

百度在 `ApolloAuto/apollo-DuerOS` 里开源了车机端库 `CarLife-Vehicle-Lib`
（Apache-2.0，Copyright 2018 The Baidu Authors）。它的
[`CConnectManager.h`](https://github.com/milesking/apollo-DuerOS/blob/master/CarLife-Vehicle-Lib/LibSource/include/CConnectManager.h)
里逐字写着：

```c
#define ADB_FORWARD_CMD     "adb forward tcp:7200 tcp:7240"
#define ADB_FORWARD_VIDEO   "adb forward tcp:8200 tcp:8240"
#define ADB_FORWARD_MEDIA   "adb forward tcp:9200 tcp:9240"
#define ADB_FORWARD_TTS     "adb forward tcp:9201 tcp:9241"
#define ADB_FORWARD_VR      "adb forward tcp:9202 tcp:9242"
#define ADB_FORWARD_TOUCH   "adb forward tcp:9300 tcp:9340"

#define LOCAL_IP_ADDR "127.0.0.1"

#define CMD_SOCKET_PORT_MD   7240      /* 手机侧 */
#define VIDEO_SOCKET_PORT_MD 8240
#define MEDIA_SOCKET_PORT_MD 9240
#define TTS_SOCKET_PORT_MD   9241
#define VR_SOCKET_PORT_MD    9242
#define TOUCH_SOCKET_PORT_MD 9340
#define CMD_SOCKET_PORT_HU   7200      /* 车机侧 */
...
```

而它的连接建立流程 [`CConnectionSetupModule.cpp`](https://github.com/milesking/apollo-DuerOS/blob/master/CarLife-Vehicle-Lib/LibSource/modules/CConnectionSetupModule.cpp)
第一行注释就是：

```cpp
int CConnectionSetupModule::connectionSetup() {
	//adb forward for video, media, tts, vr, touch channels
	CConnectManager::getInstance()->execSocketForward();
	//create socket for channels
	if(CConnectManager::getInstance()->createCmdSocket()) { ... }
```

`createCmdSocket()` 内部是 `new CSocketConnector(LOCAL_IP_ADDR, CMD_SOCKET_PORT_HU, "")`
—— **连的就是 `127.0.0.1:7200`。**

### 这和我们做的完全一样

| | 百度官方（CarLife-Vehicle-Lib） | 我们（wince-carlife） |
|---|---|---|
| 车机角色 | ADB 主机 | ADB 主机 |
| 用不用 `adb forward` | 用（6 条） | 不用命令行，直接开 6 条 `tcp:xxxx` ADB 通道 |
| 数据最终落到哪 | 车机本地 `127.0.0.1` 的 7200/8200/… | 车机本地监听的随机端口（等价） |
| 端口表 | 7240/8240/9240/9241/9242/9340 | **一模一样** |
| 通道拆分 | cmd / video / media / tts / vr / touch | **一模一样** |

> `adb forward` 和我们直接开 `tcp:` 通道，是 ADB 协议里**同一件事的两种写法**：
> `adb forward tcp:7200 tcp:7240` = 在车机 7200 端口监听，把流量送进
> ADB 的 `tcp:7240` 通道。我们省掉了本地端口号固定这一步，语义完全相同。

## 证据 ②：百度官方的车机端 App，第一条排错建议就是「开启 USB 调试」

百度开源的 Android 车机端 App `CarLife-Android-Vehicle`，它的连接帮助页面
（`assets/diagnose/androidHelpDetailsPage.html`）全文如下：

```
连接帮助
开启"USB调试"
1 点击设置
2 点击开发者选项
3 开启开发者选项
4 勾选USB调试
如果设置中找不到"开发者选项"，操作如下
1 点击关于手机
2 多次点击版本号
```

另外两条建议是「重新连接USB」「重启手机再次连接」。

而且这个车机端 App 里**直接打包了一份完整的 `platform-tools/adb` 可执行文件**
（`CarLife-Android-Vehicle/assets/sdk/platform-tools/adb`，4 MB）。

> 也就是说：**「车机开个 adb，让用户在手机上打开 USB 调试」就是百度官方的标准做法。**
> 我让你做的，和百度让车主做的，是同一件事。

## 证据 ③：vivo 官方明确说 —— Jovi InCar 就是要一台 CarLife 车机

vivo 官网客服问答（原文）：

> **「使用vivo智能车载（Jovi InCar），还需要提前安装百度CarLife+软件吗？」**
> 不需要提前安装百度CarLife+软件。支持vivo智能车载的手机机型，首次与车机连接时，
> 手机会提示安装 **CarLife组件**，安装好组件即可连接车机。
> —— [vivo 官网](https://www.vivo.com.cn/service/questions/all?categoryId=156&questionId=1090)

> **「汽车车机支持苹果CarPlay，不支持百度CarLife+，车机能否使用vivo智能车载？」**
> vivo智能车载**暂不支持**直接连接苹果CarPlay车机。
> —— [vivo 官网](https://m.vivo.com.cn/service/questions/all?categoryId=156&questionId=1088)

两条合起来说明：

1. **Jovi InCar 手机侧跑的就是「CarLife 组件」** —— 即百度 CarLife 的协议实现。
   我们做的就是 CarLife 车机端，所以在协议层是对得上的。
2. **vivo 自己说 Jovi InCar 只认 CarLife 车机**，不认 CarPlay 车机。
   而你这台车机**出厂就是一台 CarLife 车机**（自带官方的 `CECarLife.exe`、
   `adb_driver.dll`，驱动注册表项 `Drivers\USB\LoadClients\...\255_66_1\ADB_Class`）。
   换句话说：**这是官方支持的组合**，只是官方的那半个程序（CECarLife.exe）是 2017 年的。

## 证据 ④：协议常量逐条对得上（第三方独立实现佐证）

第三方协议分析工具
[`stonexu1986/carlife-protocol-analysis-tool`](https://github.com/stonexu1986/carlife-protocol-analysis-tool)
（Python，专门解析车机↔手机之间的 CarLife 报文）里，常量与我们的代码**逐条一致**：

| 含义 | 分析工具 | 我们 |
|---|---|---|
| HU 协议版本 | `0x00018001` | `CL_MSG_HU_PROTOCOL_VERSION 0x00018001` ✅ |
| 版本匹配结果 | `0x00010002` | `CL_MSG_PROTOCOL_VERSION_MATCH 0x00010002` ✅ |
| 视频编码器初始化 | `0x00018007` | `0x00018007` ✅ |
| **请求 JPEG 帧** | `0x00018056` | `CL_MSG_VIDEO_ENCODER_JPEG 0x00018056` ✅ |
| JPEG 帧 ACK | `0x00010057` | `0x00010057` ✅ |
| 视频数据通道 | `0x00020001` | ✅ |
| 触摸硬按键 | `0x00068008` | `CL_MSG_TOUCH_CAR_HARD_KEY 0x00068008` ✅ |
| HU 认证请求 | `0x00018048` | `CL_MSG_HU_AUTHEN_REQUEST 0x00018048` ✅ |
| MD 认证应答 | `0x00010049` | `CL_MSG_MD_AUTHEN_RESPONSE 0x00010049` ✅ |
| 视频包头长 | 12 字节 | `VIDEO_HEAD_LEN 12` ✅ |

包头方向约定也一样：`0x000180xx` = HU→MD，`0x000100xx` = MD→HU。

## 一个重要的对照：为什么 CarLife 比 Android Auto 好做

顺带查到一个 **[Headswap](https://github.com/YegorkaPomidorka/headswap)** 项目
（把 Android Auto 塞进只支持 CarLife 的原厂车机）。它的 README 里有一句关键的话：

> 「Android Auto 只接受由 **Google Automotive Link 签名**的车机证书。
> 公开项目里用的证书和私钥在 aasdk / headunit-revived 里……」

也就是说：**Android Auto 有一道真正的密码学大门**（没有 Google 签发的证书，
手机端直接拒绝），必须借用泄漏出来的证书。

**CarLife 没有这道门。** 它的认证只有三个 proto：

```proto
message CarlifeAuthenRequest  { required string randomValue  = 1; }  /* HU → MD */
message CarlifeAuthenResponse { required string encryptValue = 1; }  /* MD → HU */
message CarlifeAuthenResult   { required bool   authenResult = 1; }  /* HU → MD */
```

而且是 **HU 主动发起**（`0x00018048`）—— 车机不问，手机就不会问。
`bdcf` 里的 `#Channel Id: Baidu will provide the channel id to all OEM`
只是商用授权用的渠道号，不是运行时的密码学闸门。

> 这一条直接回答「这条路通不通」：**它没有不可绕过的授权关卡，
> 唯一的门槛是工程实现本身。**

## 那我们和百度官方还有什么不一样？（诚实对照）

| 项 | 百度官方 HU | 我们 | 影响 |
|---|---|---|---|
| ADB 主机 | 是（外部调 adb 命令） | 是（自己实现 ADB 协议） | 等价 |
| 通道转发 | `adb forward` | 直接开 `tcp:` 通道 | 等价 |
| 拉起手机端 | `execStartCarlife()` / `execStartBdsc()` | `am start` + `pidof` 复核 | 等价，我们少了推 `bdsc` 那步 |
| 协议版本 | 1.0 | 1.0 | 相同 |
| 认证 | 实现了 Authen 三件套 | 只保留固定串应答 | ⚠ 见下面风险 2 |
| 视频 | H.264 硬解 | 先要 JPEG，再上 H.264 软解 | ⚠ 见下面风险 4 |
| 平台 | Android 车机 | **WinCE 6.0 + ARMv4I** | ⚠ 见下面风险 4 |

## 还没被验证的四件事（这几条我必须说清楚）

1. **手机端 App 光靠 `am start` 会不会开始监听 7240？**
   官方是靠 `execStartCarlife()` 拉起来的，但我们不知道它是否还需要一个
   「检测到车机」的外部事件。→ 下次上车看第 3 阶段日志就知道。

2. **现代 CarLife 组件会不会强制要求认证？**
   Authen 是 HU 发起的，我们不发起它大概就不问；但**这条是推断**。
   → 若手机回了 `0x00010049/0x0001004B` 我们要能应对，代码里已留位置。

3. **协议版本 1.0 够不够？**
   2026 年的 CarLife 组件可能要求更高版本。→ 已有 `cl_resend_version()`，
   必要时换版本号重试。

4. **性能**：SiRF Atlas V、单核、800×480 16 位色、173 MB 可用内存，
   软解 JPEG/H.264 能不能跑到能看的帧率，**只有真机说了算**。
   → 程序里做了 5 档分辨率预设，现场逐个试。

## 一句话总结

> 我们不是在「魔改」或者「绕过」什么 ——
> **我们是在重新实现百度官方那条路，而且是对着百度自己开源的代码实现的。**
> 端口、包头、消息号、连接方式、甚至连排错提示（开启 USB 调试）都一致。
>
> 剩下的不是「路通不通」的问题，是「我这台 2007 年代的单核 WinCE 能不能扛住」的问题。
