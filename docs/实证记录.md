# 实证记录（推论必须有证据，这里是证据）

本项目的每个结论都标注证据等级。**未经实证的推断一律标明"待验证"**。

## 1. Jovi InCar 就是百度 CarLife 协议 ✅ 已确认

| 证据 | 出处 |
|---|---|
| "首次与车机连接时，手机会提示安装 **CarLife 组件**" | vivo 官网 FAQ（原文抓取） |
| "vivo 新推出了 jovi incar，**直接走百度 carlife 协议**" | 社区 |
| "Joviincar 6.0.5.5 更新，**百度 Carlife 组件更新至 8.7.1**" | 社区 |
| "只要原车机支持百度 CarLife **或亿连车联**，就能有线或无线直接连接" | 中关村在线 |

**推论**：Jovi InCar 内含 CarLife 组件，车机端只要实现 CarLife 车机端协议即可被它识别。

## 2. 车机装的那版亿连（4.4.32）完全不支持 CarLife ✅ 二进制实证

在脱壳后的 `easyconnected.exe`（2049536 字节）里搜
`carlife` / `arLife` / `jovi` / `incar` / `iccoa` / `hicar` / 甚至 `Life` 片段：
**全部 0 命中**。只命中 `AirPlayServer`。

→ 这解释了"只能连旧版亿联自家软件"的根本原因：**该版本根本没有 CarLife 协议代码**，
不是设置问题。

## 3. 该车机的 USB 传输走 ADB ✅ 二进制实证

同一二进制中发现：
- `xAdbProtocol::connect_remote`
- `xAdbProtocol::send_auth_publickey`（ADB 的 RSA 认证握手）
- 引用 DLL：`ADB_Driver.dll`、`ADBT.dll`、`VDEC_785.dll`、`VDEC_DCH60.dll`

**推论**：传输层大概率要实现 ADB host（或复用 `ADB_Driver.dll` 的导出）。
⚠ 但 **CarLife 本身是否也用 ADB 尚未验证** —— 可能是 AOA / USB 网络。

## 4. 车机只能显示一个 MessageBox ✅ 真机实证

对照实验 `WinCE-TwoBox.exe`（连续调两次 `MessageBoxW`，不做别的）
在真机上**只弹了第一个**。

**设计约束**：所有需要向用户汇报的程序，必须走「内存里拼报告 → 单弹窗」
或「真窗口 + 自绘」。这就是为什么 M1 骨架直接用真窗口。

## 5. coredll 导出表的坑 ✅ 查表实证

`COREDLL.DEF`（1661 个导出名，来自 enlyze/w32api）核对结果：

| ❌ 不导出 | ✅ 可用替代 |
|---|---|
| `TextOutW` | `DrawTextW` / `ExtTextOutW` |
| `GetTextExtentPoint32W` / `GetTextExtentPointW` | `GetTextMetricsW` |
| `lstrlenW` / `lstrcpyW` / `lstrcpynW` | `wcslen` / `wcscpy` / `wcsncpy` |
| `RtlZeroMemory`（`ZeroMemory` 会展开成它） | `memset` |
| `ExitProcess` | `ExitThread` |

**教训**：写 WinCE 代码前先查导出表，否则白等一轮 CI。

## 7. M0 里程碑 ✅ 真机跑通

手工构造（无编译器）的 WinCE ARM PE（`WinCE-M0.exe`，1024 字节）在真机上
被加载器接受、`COREDLL` 具名导入解析成功、`MessageBoxW` 正常显示预期文本。

**意义**：验证了「手工 PE → U盘 → 车机文件管理器 → 运行」这条链路完全可用。

## 主机端到端协议验证（本轮新增，已全绿）

### 做法

让【真实的 `carlife.c`】用主机 gcc 编出来，连上一个 Python 写的"假手机"，
把它发出的**每个包逐字节**拆开核对。

关键点：**期望的字节全部硬编码**在测试脚本里，不是用代码算出来的 ——
用代码算就是循环论证（同一个理解错两次会互相抵消），硬编码才是独立核对。
期望值本身另用一份独立实现交叉验算过。

覆盖：握手 → 重发版本 → VIDEO_ENCODER_INIT → START → JPEG →
收视频帧 → 触摸写法A（按下/移动/抬起）→ 触摸写法B → 硬按键，共 10 个包。

### 这一步抓到的真 bug ⭐

```c
r = select(0, NULL, &wf, NULL, &tv);          /* ✗ 错的 */
r = select((int)s + 1, NULL, &wf, NULL, &tv); /* ✓ 对的 */
```

`select` 的第一个参数必须传「最大 fd + 1」：

| 平台 | `nfds = 0` 的后果 |
|---|---|
| **WinSock（车机）** | 忽略该参数 → **照常工作** |
| **POSIX（任何标准系统）** | 一个 fd 都不检查 → **纯睡满超时** → 永远连不上 |

所以这是个**在车机上侥幸能跑、在别处必挂**的错 —— 光读代码根本看不出来，
是主机端到端测试把它逼出来的。三处 `select` 全部已修，并加了注释防止被"优化"回去。

### 踩过的三个测试脚手架坑（记下来别再犯）

1. **中文引号写进 C 字符串** → 编译器把 `"` 当成字符串结束符，编译失败。
2. **诊断程序借用了被测目标的端口（7240）** → 假手机的 `accept()` 先接到的
   是诊断连接，真正的协议连接被晾在队列里。现象是"发送成功但对方收不到"，
   极具误导性。**结论：诊断绝不能借用被测目标正在用的端口。**
3. **崩溃时输出丢失** → 程序输出被管道捕获时 stdout 是全缓冲的，一旦中途
   崩溃，缓冲区内容全部丢失，完全看不到它走到哪一步。必须 `setvbuf` 设无缓冲。

另外主机侧要 `signal(SIGPIPE, SIG_IGN)`：Windows 的 socket 从不产生 SIGPIPE，
忽略它才是与车机行为对齐，否则会以退出码 -13「假崩溃」。
