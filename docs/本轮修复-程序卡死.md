## 二、上一版那个致命 bug（已经修掉）

从第 35 秒开始，日志里是这么一万多行：

```
[35.315]  XX  ← 上一个 ADB 句柄还在收尾（读线程未退出），本轮先跳过
[42.383]  XX  ← 上一个 ADB 句柄还在收尾（读线程未退出），本轮先跳过
   ……一直重复到 1277 秒，共 308 次……
```

后面 **1242 秒**程序什么都做不了，一直在原地打转。

### 原因：我自己在上一版里埋的

上一版我给设备加了个「专用读线程 + 环形缓冲」。其中往缓冲里放数据的地方是这么写的：

> 缓冲满了 → 睡 2 毫秒 → 再试

看着挺无害，**但那是个 while 死循环**。后果是连锁的：

```
读线程卡在「缓冲区满」的死循环里
   → 再也回不到外层循环
   → 永远看不到「该退出了」的标志
   → 句柄永远收不了尾
   → 下一轮永远开不了设备
   → 程序从这一刻起彻底卡死
```

日志里三个数字把这条链子钉得死死的：

| 日志证据 | 说明 |
|---|---|
| `环形缓冲还剩 524288 字节（容量 524288）` | 缓冲**一直是满的** |
| `缓冲满丢过 38068 次` → 一路涨到 `393417 次` | 约 **300 次/秒**，正好是每 2 毫秒兜一圈 |
| `上一个 ADB 句柄还在收尾` × 308 次 | 从 35 秒一直卡到 1277 秒 |

### 这一版怎么修的

1. **缓冲满了就丢，绝不在里面等。** 丢的时候挤掉最老的数据，保留最新的。
   这是一条我们跟不上的字节流，**丢掉远好过卡死**。
2. **「关设备」这条路径整个重写了**，规则短到不可能卡住：
   - 读线程**还活着** → 说明这个句柄是好的（它一直在读），那就**不关**，
     只把缓冲里的旧数据倒掉，句柄留着下一轮接着用；
   - 读线程**已经退出**（设备拔了/出错了）→ 它手里没有等待中的读，
     这时候关句柄是安全的，就真的关掉、清干净。
   这样「等一个永远不退出的人」这件事从设计上就不存在了。
3. 顺带把读线程的统计**单独报出来**（设备侧读到多少 / 读了几次 / 单次最大多少），
   和「协议层收到多少」分开。上一版混在一起，所以现场只看到「收到 24 字节」，
   完全看不出设备其实吐了 512KB。

## 三、顺手修掉的另外两个真 bug

### ① 读包读到一半超时，会把字节丢掉 → 整条流永久错位

日志里的形状是这样的：

```
[11.495] [握手] 等手机应答超时
[13.530] [握手] 已发 CNXN，等手机应答
[14.134] [握手] 读设备失败  (0x2)      ← magic 对不上，流已经错位
```

设备是**字节流**，一个包常常分几次到。原来的写法是「读不够就返回超时」，
**而已经读到的那半截包被丢掉了** —— 下一次再读就从包的中间开始解，
从此每个包都会 magic 校验失败（-2）。

现在改成：**超时就把进度留着，下次接着读，一个字节都不丢。**

### ② `ADB` 结构里带着需要释放的指针 —— 电脑上的联调程序直接段错误

这个被 CI 抓到了（退出码 -11）。原因是结构里有 `unsigned char *rx`
这种「需要 free 的成员」，而我在重连路径上写了「先 free 再清零」——
**如果调用方传进来的是没清零的栈变量，那就是 free 一个野指针。**

车机上 `g_adb` 是静态变量（本来就是 0）所以没暴露，但这是个真缺陷。

现在整个 `ADB` 结构里**一个指针都没有**（缓冲全部搬到 adb.c 的文件级数组），
`memset` 怎么用都安全，也不存在需要调用方配合的约定。

## 四、这一趟还有个坏消息：手机那边这次没应答

```
[3.457] 已发 CNXN，等手机应答
[6.463] 等手机应答超时
[8.490] 已发 CNXN，等手机应答
[11.495] 等手机应答超时
[13.530] 已发 CNXN，等手机应答
[14.134] 读设备失败
[26.241] CNXN 写设备失败
```

前两趟是能收到 AUTH / CNXN 的，这趟手机一个字都没回。
最可能的两个原因：
- **手机上「USB 调试」的授权被撤销了**（换了 USB 口、或手机重启过）；
- 或者手机当时弹了「允许 USB 调试」的框没点。

👉 **下一趟请特别留意手机屏幕**：插上线之后应该弹「是否允许 USB 调试？」
→ 勾「一律允许」→ 点「允许」。这是这趟唯一没走通的一环。
